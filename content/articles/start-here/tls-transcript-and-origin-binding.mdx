# TLS transcript와 origin binding

## Reader Question

서버 인증서와 TLS 1.3 Finished를 확인했다면, 특정 HTTP 응답이 그 서버에서 왔다고 제3자에게 보여 줄 수 있을까? 세션의 인증 맥락을 확인하는 일과 응답 provenance를 공개 검증하게 하는 일은 범위가 다르다.

## Why It Matters

tls-transcript는 handshake 중 교환된 메시지의 맥락이다.

TLS 1.3에서 CertificateVerify와 Finished는 transcript hash에 결합되어 서버 인증과 handshake 무결성을 확인한다. 이는 클라이언트가 자신이 연결한 peer를 인증하는 데 중요하다.

certificate identity는 신뢰하는 CA와 hostname 검증 같은 애플리케이션 규칙을 전제한다.

이 전제를 충족해도 특정 HTTP 응답 전체가 제3자에게 provenance를 가진다는 결론은 나오지 않는다.

## Core Model

certificate identity는 서버가 제시한 인증서와 연결하려는 hostname 등을 검증해 peer identity를 판단하는 맥락이다.

certificate-verify는 TLS 1.3의 `CertificateVerify` 메시지다. 인증서 개인 키 보유를 transcript 관련 내용에 결합한다.

finished-message는 handshake가 합의한 비밀과 transcript 맥락에 대한 확인을 제공한다.

origin-binding은 이후 설계에서 “이 공개 claim이 어떤 origin의 어떤 세션 자료와 연결되는가”를 명시하는 작업이다. TLS endpoint authentication은 이 결합의 유용한 입력이지만, 그 자체가 제3자용 claim 형식은 아니다.

## Protocol or System Artifact

TLS 1.3 문맥에서는 certificate chain, `CertificateVerify`, `Finished`, transcript hash를 함께 읽어야 한다. 하나의 인증서 파일만 떼어 내 HTTP body의 진실성을 보이는 산출물로 취급하면 안 된다.

TLS 1.2는 별도 handshake 구조를 쓴다. TLS 1.3의 `CertificateVerify` 표현을 TLS 1.2 일반 설명으로 확장할 수 없고, 인증·키 교환·Finished 구성은 버전과 cipher suite에 따라 구분해 확인해야 한다.

## Failure Mode

“인증서가 있으니 이 JSON은 서버가 서명했다”는 주장은 과장이다. 인증서는 연결 peer 인증에 쓰이며, HTTP 응답을 독립 verifier가 검사할 수 있는 공개 증명으로 자동 변환하지 않는다.

TLS 1.2와 1.3을 한 문장으로 뭉치면 실제 검토 대상 메시지와 키 수립 경로가 흐려진다.

## Minimal Lab or Trace

`https://api.example/membership` 응답을 받았다고 하자. 브라우저는 TLS 1.3 handshake에서 서버 identity와 Finished를 확인한 뒤 보호된 응답을 해석한다. 제3자가 `tier=gold`를 검증하려면, 어떤 origin과 transcript 맥락에 어떤 응답 bytes와 parser 결과를 묶었는지 추가 규칙이 필요하다.

## zkTLS Bridge

zkTLS의 출처 결합은 TLS handshake를 무시하지 않지만, 그것만으로 끝나지도 않는다. 다음 글에서는 record의 대칭키 인증이 왜 독립 verifier의 공개 검증과 다른지 설명한다.

## Verification Checklist

- `CertificateVerify`와 `Finished`를 TLS 1.3에 한정했는가?
- certificate identity의 검증 전제를 밝혔는가?
- 세션 인증과 HTTP 응답 provenance를 분리했는가?
- TLS 1.2의 구조를 별도로 확인해야 한다고 했는가?
