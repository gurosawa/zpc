# Verifiable credentials와 anonymous credentials

## Reader Question

credential claim을 검증하면서 holder의 불필요한 속성을 숨길 수 있을까? Verifiable Credential은 issuer가 subject에 대한 claim을 만들고 holder가 이를 보관했다가 verifier에게 presentation하는 모델이다. Anonymous credential은 여기에 selective disclosure, unlinkability, predicate proof 같은 privacy layer를 얹는다.

W3C VC Data Model 2.0은 2025년 W3C Recommendation이며 issuer, holder, verifier, verifiable data registry 역할을 정의한다. VC Overview는 verifiable presentation이 holder가 verifier에게 claim을 제시하는 구조이고, privacy를 위해 필요한 persona subset만 표현하는 것이 중요하다고 설명한다. 하지만 VC data model 자체가 자동으로 anonymous credential을 만드는 것은 아니다. 사용한 securing mechanism과 presentation protocol이 privacy를 결정한다.

## Why It Matters

zkTLS는 웹 origin에서 나온 데이터를 credential-like claim으로 바꿀 수 있다. 예를 들어 은행 사이트에서 "잔고가 기준 이상"이라는 proof를 만들고, 이를 대출 verifier에게 제출할 수 있다. 이때 원본 origin은 bank server이고, credential ecosystem에서는 issuer, holder, verifier role이 생긴다. 두 모델을 섞어 쓰면 누가 claim을 보증하는지 흐려진다.

VC에서 issuer는 claim authority다. zkTLS에서 origin server는 TLS response source다. 사용자가 response를 proof로 만들었다고 해서 origin이 VC issuer로 의도적으로 credential을 발행한 것은 아니다. 이 차이를 놓치면 verifier가 "TLS origin에서 읽은 사실"을 "issuer가 credential로 보증한 사실"로 오해한다.

anonymous credential의 목표는 필요한 claim만 보여주고 presentation 간 correlation을 줄이는 것이다. 하지만 credential id, subject id, issuer key, status check, disclosed attribute 조합, timestamp, wallet telemetry가 남으면 unlinkable proof도 추적될 수 있다.

## Core Model

VC role model:

```txt
Issuer
  asserts claims
  issues credential

Holder
  stores credential
  creates presentation

Verifier
  verifies proof
  validates claim by policy
```

anonymous presentation model:

```txt
credential:
  many claims
  issuer proof
  status metadata

presentation:
  selected claims
  challenge
  audience
  holder binding
  derived proof
```

verification과 validation은 다르다.

| step | question |
|---|---|
| verification | proof, issuer, integrity, status가 맞는가? |
| validation | 이 issuer와 claim을 이 상황에서 믿을 것인가? |

W3C VC Data Model도 verifiability가 underlying claim의 truth를 의미하지 않는다고 경계한다. verifier는 issuer, proof, subject, claims를 자기 policy로 평가해야 한다.

## Protocol or System Artifact

VC artifact:

```txt
credential:
  context
  type
  issuer
  credentialSubject
  validFrom
  status
  proof or securing envelope
```

presentation artifact:

```txt
presentation:
  selected credential data
  verifier challenge
  audience
  proof
  holder binding when required
```

securing mechanisms:

```txt
Data Integrity:
  cryptographic proof on document

JOSE/COSE:
  JWT, SD-JWT, COSE envelope

BBS:
  base credential proof
  derived selective proof

Status List:
  revocation or suspension signal
```

W3C VC JOSE-COSE Recommendation defines securing VCs and VPs with JOSE, SD-JWT, and COSE. RFC 9901 defines SD-JWT as selective disclosure for JSON data inside JWS/JWT. BBS cryptosuite defines proof generation and proof verification for selective disclosure and unlinkable proof in the VC Data Integrity model.

credential status도 artifact다. active, revoked, suspended, expired 같은 상태는 credential proof와 별도로 변할 수 있다. verifier가 status를 확인하지 않으면 오래된 credential을 받아들일 수 있고, status를 확인하는 방식이 holder privacy를 누출할 수도 있다. Bitstring status list는 상태 정보를 bitstring으로 표현해 status distribution을 표준화하는 방향을 제공한다.

```txt
verification package:
  credential proof
  presentation proof
  challenge
  audience
  status reference
  verifier policy
  validation result
```

## Failure Mode

첫 번째 실패는 full credential presentation이다. verifier가 필요한 것은 "성인 여부"인데 holder가 name, birthdate, address, issuer id, credential id를 모두 제출하면 VC는 privacy-preserving 도구가 아니라 structured oversharing이 된다.

두 번째 실패는 verifiability와 truth를 혼동하는 것이다. proof가 valid하다는 것은 credential이나 presentation이 tamper-evident하고 issuer key로 검증된다는 뜻이다. issuer가 믿을 만한지, claim이 최신인지, claim이 business policy에 맞는지는 별도 validation이다.

세 번째 실패는 long-lived identifier correlation이다. `credentialSubject.id`, email, government id, wallet id, key id가 반복되면 selective disclosure를 해도 presentations가 연결된다. 익명성을 원하면 identifier minimization과 pairwise 또는 unlinkable presentation을 설계해야 한다.

네 번째 실패는 status check tracking이다. revocation/status check가 매 presentation마다 issuer나 registry에 직접 닿으면 verifier와 holder의 활동이 추적될 수 있다. status list 설계, caching, privacy-preserving status check를 함께 봐야 한다.

다섯 번째 실패는 bearer credential theft다. holder binding이 없으면 credential presentation을 훔친 공격자가 replay할 수 있다. RFC 9901은 SD-JWT에서 optional key binding을 정의하고, verifier policy가 필요할 때 holder가 private key possession을 보여야 한다.

여섯 번째 실패는 BBS unlinkability를 전체 privacy로 과장하는 것이다. BBS proof가 signature value와 unlinkable해도 disclosed claims가 희귀하거나 message count, header, context, issuer, timing이 같으면 correlation이 가능하다.

일곱 번째 실패는 zkTLS origin을 issuer로 오해하는 것이다. bank website가 TLS response를 제공했어도, bank가 W3C VC issuer로 credential을 발행한 것이 아닐 수 있다. zkTLS proof wrapper가 issuer 역할을 맡는다면 그 issuer는 notary, wallet, user, service 중 누구인지 명확히 해야 한다.

여덟 번째 실패는 status privacy를 단일 boolean으로 보는 것이다. credential이 revoked인지 확인하는 것은 필요하지만, status 조회가 verifier, holder, credential id, 시간 정보를 issuer나 registry에 알려줄 수 있다. Bitstring status list 같은 구조는 대량 상태 정보를 담아 개별 조회 correlation을 줄이는 방향을 제공하지만, caching, list size, update cadence, verifier logging이 여전히 privacy surface다.

아홉 번째 실패는 holder binding을 항상 privacy-enhancing으로 보는 것이다. holder binding은 stolen presentation replay를 막지만, 같은 holder key를 여러 verifier에게 쓰면 correlation vector가 된다. audience, challenge, pairwise key, presentation-specific proof가 왜 필요한지 policy로 정해야 한다.

열 번째 실패는 derived predicate의 semantics를 verifier가 이해하지 못하는 것이다. "ageOver21"은 편리하지만 어떤 date source, timezone, issuance date, validity period, revocation status를 기준으로 계산했는지 모르면 verifier policy가 약해진다. anonymous credential에서도 predicate definition은 public schema로 남아야 한다.

열한 번째 실패는 wallet을 passive storage로만 보는 것이다. holder wallet은 verifier request를 해석하고, 어떤 credential을 쓸지 고르고, user consent를 받고, presentation을 생성한다. wallet이 malicious하거나 confused deputy가 되면 verifier가 과도한 claim을 요청했을 때 사용자가 알아차리지 못한다. VC privacy는 credential format뿐 아니라 wallet mediation에 달려 있다.

열두 번째 실패는 audience binding 없이 presentation을 재사용하는 것이다. presentation이 특정 verifier, challenge, transaction에 묶이지 않으면 다른 verifier에게 전달될 수 있다. anonymous credential도 replay protection과 audience restriction이 필요하다.

## Minimal Lab or Trace

lab:

```txt
credential claims:
  name
  birthdate
  country
  member tier
  account status

presentations:
  full JWS VC
  SD-JWT with country only
  BBS derived proof for ageOver21
```

compare:

| presentation | disclosed | correlators |
|---|---|---|
| full VC | all claims | many |
| SD-JWT | selected claims | issuer, key binding |
| BBS derived | selected messages | disclosed pattern |

negative tests:

```txt
reuse credential id:
  correlation

omit challenge:
  replay

skip status check:
  stale credential

status check online:
  tracking risk

confuse issuer:
  trust failure
```

이 lab은 credential format 경쟁이 아니다. 같은 claim을 어떤 presentation surface로 내보낼 때 privacy와 verification semantics가 어떻게 달라지는지 보는 것이다.

policy worksheet:

| verifier need | acceptable proof |
|---|---|
| age over 21 | predicate proof |
| country eligibility | selected country |
| active membership | status plus freshness |
| account ownership | holder binding |

이 worksheet는 verifier가 raw claim을 요구하지 않고도 reliance decision을 할 수 있는지 묻는다. verifier policy가 raw birthdate를 요구하면 anonymous credential 기술이 있어도 최소 공개가 작동하지 않는다.

correlator inventory:

```txt
stable:
  subject id
  credential id
  holder key

contextual:
  issuer id
  status endpoint
  claim combination
  timestamp

protocol:
  challenge reuse
  proof format
  wallet metadata
```

presentation design은 이 inventory를 줄이는 작업이다. 모두 제거할 수 없으면 verifier에게 어떤 correlator가 남는지 명시해야 한다.

## zkTLS Bridge

zkTLS proof는 웹 origin에서 읽은 값을 credential ecosystem으로 가져올 수 있다. 예를 들어 "payroll site의 employment status가 active"라는 TLS-origin proof를 holder가 verifier에게 제출할 수 있다. 이때 설계 선택지는 여러 가지다.

```txt
direct proof:
  verifier checks zkTLS proof

holder credential:
  wallet stores derived claim

notary-issued credential:
  notary signs transcript receipt

issuer bridge:
  origin later issues VC
```

각 선택은 trust를 다르게 만든다. direct proof는 origin TLS provenance에 가깝고, notary-issued credential은 notary trust가 들어가며, origin-issued VC는 issuer trust 모델에 들어간다. anonymous credential layer는 재사용 가능성을 높이지만, transcript URL, timestamp, notary signature, account-specific field가 correlation surface가 된다.

좋은 bridge rule:

```txt
separate:
  TLS origin provenance
  credential issuer authority
  holder presentation privacy
  verifier reliance policy
```

이 분리를 지키면 zkTLS proof를 VC처럼 포장하더라도 claim authority를 과장하지 않는다.

재사용 가능한 zkTLS-derived credential을 만들 때는 freshness가 가장 어려운 축이다. 웹 response는 credential issuance처럼 장기 유효 claim으로 설계되지 않았을 수 있다. 오늘의 bank balance proof를 내일의 credential로 재사용하려면 validity period, refresh policy, revocation 또는 supersession rule이 필요하다. 그렇지 않으면 privacy는 좋아져도 verifier가 stale fact에 의존한다.

따라서 zkTLS-derived credential은 "origin observed fact"와 "issuer asserted fact"를 분리해 표기하는 것이 좋다. former는 특정 시간의 TLS response에 대한 provenance이고, latter는 issuer가 정책적으로 주장한 credential이다. 이 distinction이 있어야 verifier가 freshness, liability, dispute handling을 올바르게 판단한다.

## Verification Checklist

- issuer, holder, verifier 역할을 구분했는가?
- verification과 validation을 분리했는가?
- VC data model과 securing mechanism을 혼동하지 않았는가?
- selective disclosure, holder binding, status check를 artifact로 다뤘는가?
- full credential oversharing과 identifier correlation을 failure mode로 포함했는가?
- BBS/SD-JWT unlinkability를 metadata privacy와 함께 다뤘는가?
- zkTLS origin provenance와 credential issuer trust를 분리했는가?
