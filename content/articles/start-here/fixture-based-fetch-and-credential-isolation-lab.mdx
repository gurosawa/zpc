# fixture 기반 Fetch·credential 격리 실습

## Reader Question

실제 계정·토큰·개인정보 없이 Fetch와 공개 범위를 어떻게 시험할까? 이 실습은 네트워크 대신 합성 fixture를 읽고, allowed Origin·request scope·challenge 가정·disclosure manifest를 대조한다. 통과 결과는 해당 입력에서 교육용 검사기가 정한 대로 동작했다는 뜻일 뿐 production 보안 보장이 아니다.

## Why It Matters

실습을 편하게 하려고 실제 bearer token이나 인증 쿠키를 파일에 넣으면 credential 격리 원칙부터 깨진다. RFC 6750은 bearer token을 소지한 주체가 사용할 수 있는 값으로 다룬다. 따라서 이 실습에는 실제 접근 권한을 주는 값을 넣지 않는다.

fixture와 manifest는 TLSNotary나 RFC가 정한 프로토콜 형식도 아니다. 학습자가 입력·공개 범위·실패 이유를 재현하도록 이 프로젝트가 정의한 교육용 산출물이다.

## Core Model

안전 경계는 세 칸으로 나뉜다.

1. **fixture 입력**에는 `.invalid` Origin, 합성 응답, 교육용 challenge만 둔다.
2. **private 경계**에는 실제 token·쿠키·개인정보가 없어야 한다. 발견하면 실행 전에 중단한다.
3. **공개 산출물**에는 manifest가 허용한 필드와 검사 결과만 둔다.

freshness는 challenge 문자열 하나로 확정되지 않는다. 이 실습은 발급 주체·audience·유효 시간·재사용 정책을 가정으로 기록하되 실제 replay 방지 구현을 주장하지 않는다.

## Protocol or System Artifact

다음처럼 비밀이 없는 fixture를 만든다.

```json
{
  "labOnly": true,
  "containsRealCredential": false,
  "containsPersonalData": false,
  "request": {
    "origin": "https://fixture.example.invalid",
    "method": "GET",
    "path": "/api/status",
    "challenge": "demo-challenge-001"
  },
  "response": {
    "status": 200,
    "body": {
      "eligible": true,
      "internalNote": "synthetic-do-not-disclose"
    }
  }
}
```

disclosure manifest는 공개 계약만 기록한다.

```yaml
allowedOrigin: https://fixture.example.invalid
requestScope: GET /api/status
audience: https://verifier.example.invalid
freshnessAssumption: demo-only; no replay guarantee
disclose:
  - /body/eligible
exclude:
  - /body/internalNote
```

manifest에는 실제 credential 값이나 개인정보를 적지 않는다. `disclose`와 `exclude`는 교육용 field path이며, 특정 TLSNotary artifact 형식을 흉내 내는 것이 아니다.

## Failure Mode

- 실제 계정, 실제 bearer token, 인증 쿠키, 개인정보가 있으면 즉시 중단한다.
- Origin·method·path가 manifest와 다르면 request scope 검사에서 거절한다.
- manifest가 `/body/internalNote`를 공개하면 privacy policy 위반으로 검출한다.
- challenge가 다르더라도 이를 비교하도록 구현하지 않았다면 자동 거절을 기대하지 않는다.
- fixture 통과를 TLS provenance, ZK soundness, production credential 격리의 증거로 일반화하지 않는다.

## Minimal Lab or Trace

1. 위 두 파일을 로컬 임시 입력으로 준비한다. 네트워크 요청은 보내지 않는다.
2. `labOnly`, `containsRealCredential`, `containsPersonalData`를 먼저 검사한다. 첫 값은 `true`, 나머지는 `false`여야 한다.
3. fixture의 Origin·method·path를 manifest와 정확히 비교한다.
4. manifest의 `disclose`만 결과 객체에 복사하고 `exclude`가 결과에 없는지 검사한다.
5. challenge와 audience를 비교한다. 이 검사는 교육용 policy gate이며 범용 freshness 프로토콜이 아니다.
6. 결과에 `fixture-only`, `checked-inputs`, `disclosed-paths`, `limitations`를 남긴다.

다음 변형을 하나씩 실행한다.

| 변형 | 기대 결과 | 이유 |
|---|---|---|
| Origin 변경 | reject | allowed Origin 검사 |
| path 변경 | reject | request scope 검사 |
| `internalNote` 공개 추가 | detect | disclosure policy 위반 |
| challenge 변경 | 조건부 reject | 실제 비교 gate가 있을 때만 |
| 실제 secret 표시값 추가 | abort | lab 안전 경계 위반 |

성공 결과는 “이 fixture와 manifest에서 선언한 비교가 통과했다”로만 해석한다.

## zkTLS Bridge

앞 글은 mismatch가 binding되고 검사될 때에만 거절된다고 설명했다. 이 실습은 그 원칙을 비밀 없는 fixture와 manifest에 적용했다. 다음 실습에서는 public input·witness·constraint·policy gate를 분리해 wrong path·stale·policy mismatch가 실제로 모델링된 경우에만 reject되는지 확인한다.

## Verification Checklist

- 실제 계정·token·쿠키·개인정보가 없는가?
- 모든 Origin이 `.invalid`이고 네트워크 호출이 없는가?
- allowed Origin, request scope, 공개 field가 manifest에 있는가?
- challenge를 범용 replay 방지로 설명하지 않았는가?
- over-disclosure를 cryptographic failure와 구분했는가?
- fixture 형식을 TLSNotary 또는 RFC 요구사항으로 제시하지 않았는가?
- 결과를 production 보안 보장으로 일반화하지 않았는가?
