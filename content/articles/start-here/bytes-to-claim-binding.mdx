# Bytes-to-claim binding

## Reader Question

HTTP 응답 bytes가 있다고 해서 claim의 의미가 자동으로 정해지지는 않는다. bytes를 어떤 parser로 읽고 어떤 경로와 조건을 적용하는지가 함께 고정되어야 한다.

## Why It Matters

같은 JSON 텍스트라도 구현의 해석 규칙이 다르면 다른 값에 도달한다. verifier가 proof만 확인하고 parser 규칙을 확인하지 않으면, prover와 verifier는 서로 다른 claim을 가리킨다.

## Core Model

parser binding은 원본 bytes와 parser 규칙을 연결하는 설계다. parser profile은 그 규칙을 한 가지로 고정해, 같은 bytes를 같은 구조로 읽게 한다.

그 결과에서 field path와 predicate를 적용해 공개 claim을 만든다. disclosure boundary는 이 과정에서 외부에 보낼 값과 숨길 값을 가르는 경계다.

RFC 8259는 JSON canonicalization을 정의하지 않는다. 객체 이름은 유일해야 하며, 중복 이름은 구현에 따라 마지막 값 선택, 오류, 모든 쌍 노출처럼 다르게 처리될 수 있다. 따라서 profile은 중복 이름을 거부하고 숫자·문자열·경로 규칙을 명시해야 한다.

canonicalization은 재서명·재해시 또는 여러 구현 간 동일 표현이 필요할 때 profile에서 정한다. 원본 bytes와 단일 결정적 parser를 직접 증명한다면 항상 필요한 단계는 아니다.

## Failure Mode

`role`이라는 이름이 두 번 나왔을 때 prover는 마지막 값을, verifier는 첫 값을 읽는다면 같은 응답에서 상반된 claim이 나온다. 원인은 bytes가 아니라 해석 규칙이 달랐기 때문이다.

field path가 배열 순서나 누락값을 어떻게 다루는지도 고정하지 않으면, verifier가 확인한 relation과 사람이 읽는 claim의 대상이 흔들린다.

## Minimal Lab or Trace

profile에 parser 버전, 중복 이름 거부, 숫자와 문자열의 허용 형식, field path, predicate를 적는다. 이후 같은 bytes를 두 parser에 넣어 결과가 다르면 해당 입력을 수락하지 않는지 확인한다.

## zkTLS Bridge

proof relation은 bytes 자체가 아니라 명시한 입력과 관계를 확인한다. parser binding이 있어야 그 관계가 사람이 읽는 application claim에 연결된다.

## Verification Checklist

- 원본 bytes와 parser profile을 함께 식별하는가?
- 중복 JSON 이름을 거부하는가?
- field path와 predicate의 해석 규칙이 고정됐는가?
- RFC 8259가 canonicalization을 정의한다고 쓰지 않았는가?
