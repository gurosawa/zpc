# HTTPS 보호 경로: handshake와 record

## Reader Question

브라우저의 HTTP 요청은 언제부터 보호되는가? TLS는 먼저 handshake로 안전한 통신 맥락을 세우고, 그다음 record protocol로 application data를 보호한다. 두 단계의 목적을 섞지 않는 것이 중요하다.

## Why It Matters

TLS handshake는 peer 인증, 암호 모드 협상, 공유 키 자료 수립을 수행한다. 상대가 누구인지와 어떤 보안 매개변수를 사용할지 합의하는 단계다. 이후 record protocol은 그 결과로 얻은 traffic key를 사용해 application data를 record 단위로 보호한다.

HTTPS 응답의 JSON이나 HTML은 protected application data가 될 수 있다. 그러나 TLS는 데이터를 받은 사람이 그 내용을 제3자에게 자동으로 서명해 주는 프로토콜은 아니다. 연결 안의 보호와 공개 검증 가능한 provenance는 다른 요구다.

## Core Model

handshake는 연결을 시작하는 협상이다. endpoint authentication은 이 과정에서 상대 endpoint를 인증하는 규칙과 결과를 가리킨다.

traffic key는 handshake 결과를 바탕으로 이후 특정 방향의 레코드를 보호하는 데 쓰이는 키 자료다.

tls-record는 보호된 전송 단위다. record 하나가 HTTP 메시지의 의미 단위와 정확히 일치한다고 가정하면 안 된다. application은 보호된 bytes를 다시 HTTP와 JSON 같은 형식으로 해석한다.

## Protocol or System Artifact

TLS 1.3은 최신 TLS 구조를 설명하는 RFC 8446에, TLS 1.2는 RFC 5246에 각각 정의돼 있다. 두 버전의 handshake와 키 수립 구조는 다르지만, 이 글의 높은 수준 모델에서는 handshake가 통신 맥락을 만들고 record가 이후 트래픽을 보호한다는 역할 분리를 사용한다.

검토할 산출물도 나눈다. 인증서와 handshake 메시지는 세션 맥락의 일부다.

protected record는 보호된 전송 데이터다.

HTTP 응답 claim은 application이 parser 규칙으로 읽어 만든 별도의 의미 단위다.

## Failure Mode

handshake 성공을 HTTP 응답의 공개 서명으로 해석하면 안 된다.

record가 암호화됐다는 사실만으로 origin, 요청 경로, 응답 필드, 제3자 검증 규칙까지 고정됐다고 볼 수도 없다.

TLS 1.2 설명에 TLS 1.3의 세부 메시지 이름을 그대로 가져오는 혼용도 피해야 한다.

## Minimal Lab or Trace

브라우저가 `https://api.example`에 요청한다고 생각해 보자. 먼저 TLS handshake가 상대와 보안 매개변수를 정하고 traffic key 자료를 수립한다. 그 뒤 요청과 응답은 보호된 record로 흐른다. 브라우저는 record를 열어 HTTP 응답을 해석하지만, 그 해석 결과를 다른 verifier가 재현하려면 추가 산출물과 규칙이 필요하다.

## zkTLS Bridge

zkTLS는 TLS 보호를 출발점으로 삼되, 제3자가 무엇을 확인할지 별도로 설계한다. 다음 글에서는 TLS 1.3 transcript가 세션 인증 맥락에 어떻게 결합되는지 살핀다.

## Verification Checklist

- handshake와 record의 역할을 분리했는가?
- traffic key가 record 보호에 쓰인다는 범위만 주장했는가?
- TLS가 HTTP 응답을 제3자에게 자동 서명한다고 쓰지 않았는가?
- TLS 1.2와 1.3의 세부 구조를 혼용하지 않았는가?
