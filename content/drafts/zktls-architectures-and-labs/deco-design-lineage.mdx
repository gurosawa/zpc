# DECO 계열 설계

## Reader Question

DECO는 무엇을 제안했는가? DECO는 TLS로 접근한 web data가 특정 website에서 왔음을 사용자가 제3자에게 증명하고, 선택적으로 그 data에 대한 statement를 zero-knowledge로 증명하는 architecture를 제안했다. 논문 abstract는 server-side modification이나 trusted hardware 없이 이 문제를 다룬다고 설명한다.

DECO의 핵심은 oracle이다. smart contract나 외부 application은 웹 service 안의 private data를 직접 볼 수 없고, 사용자는 privacy를 잃지 않고 claim을 전달하고 싶다. DECO는 TLS session에서 얻은 데이터를 oracle/verifier가 신뢰할 수 있는 proof로 옮기는 구조를 제안한다.

## Why It Matters

zkTLS라는 이름을 쓰지 않더라도 문제는 같다. 사용자는 웹 서비스 안에 locked-up private data를 갖고 있고, 다른 system은 그 data의 provenance를 확인하고 싶다. DECO paper는 financial smart contracts, legacy credential to anonymous credentials, price discrimination claim 같은 use case를 제시했다.

DECO project site도 oracle이 trusted websites에서 data를 얻지만 privacy-sensitive web-session data를 안전하게 접근하기 어렵다고 설명한다. DECO는 cryptographic techniques로 사용자가 TLS session에 대한 fact를 oracle에게 증명하면서 password, birthdate, name 같은 민감 정보를 숨기는 예를 든다.

이 장에서 DECO는 "특정 구현을 그대로 쓰라"는 추천이 아니다. zkTLS가 어떤 problem statement에서 나왔고, TLS provenance, selective disclosure, ZK predicate, oracle trust가 어떻게 연결되는지 보여주는 reference다. 구현 가정, TLS version, modern browser constraints는 별도로 검증해야 한다.

## Core Model

DECO-style mental model:

```txt
User or Prover
  accesses web data over TLS

Web Server
  does not need modification

Oracle or Verifier
  receives provenance proof
  verifies selected statement

Application
  relies on verified claim
```

claim layers:

```txt
data provenance:
  came from website W

selective disclosure:
  reveal only field P

zero-knowledge:
  prove predicate Q

application reliance:
  accept under policy V
```

DECO는 이 layers를 oracle use case로 묶는다. TLSNotary는 similar problem을 modern protocol artifact와 developer documentation으로 다룬다. 둘을 비교하면 zkTLS architecture spectrum이 보인다.

## Protocol or System Artifact

DECO architecture flow:

```txt
1. user connects to web server
2. TLS session data obtained
3. prover creates provenance proof
4. prover hides sensitive fields
5. verifier checks statement
6. oracle relays accepted fact
```

use-case table:

| use case | raw data | public claim |
|---|---|---|
| finance | balance | above threshold |
| identity | birthdate | over age limit |
| health | steps | goal satisfied |
| commerce | receipt | purchase happened |

comparison artifact:

| axis | DECO | TLSNotary |
|---|---|---|
| framing | decentralized oracle | data portability |
| server change | no | no |
| privacy | ZK statements | redaction and ZK |
| protocol docs | paper | developer docs |
| TLS caveat | paper-specific | TLS 1.2 now |

이 표는 superiority ranking이 아니다. DECO는 연구 lineage를, TLSNotary는 current developer-facing protocol vocabulary를 제공한다.

DECO-style system에는 두 가지 verification path가 있다. 하나는 provenance path다. data가 특정 website에서 왔음을 보여준다. 다른 하나는 predicate path다. data 자체를 숨기고 claim만 보여준다. product가 이 둘을 하나로 합치면 "어디서 왔는가"와 "무엇을 만족하는가"가 섞인다.

```txt
provenance path:
  TLS session
  website identity
  data binding

predicate path:
  private data
  statement
  zero-knowledge proof
```

## Failure Mode

첫 번째 실패는 DECO를 "모든 TLS에서 즉시 사용 가능"으로 과장하는 것이다. 논문과 project site의 claim은 특정 design과 가정에 대한 것이다. modern TLS 1.3, ECH, browser security boundary, mobile app traffic, certificate pinning, anti-bot behavior는 별도 구현 문제다.

두 번째 실패는 oracle trust를 숨기는 것이다. oracle이 proof를 검증하고 application에 fact를 전달하면, application은 oracle implementation, verifier policy, proof validation을 신뢰한다. cryptographic proof가 oracle 운영 리스크를 없애지는 않는다.

세 번째 실패는 predicate semantics를 약하게 정의하는 것이다. "account balance above threshold"가 어떤 account, 어떤 currency, 어떤 timestamp, pending transaction 포함 여부를 말하는지 정의하지 않으면 proof가 valid해도 application decision이 잘못될 수 있다.

네 번째 실패는 server response variability를 무시하는 것이다. 같은 endpoint라도 locale, account type, experiment bucket, device, anti-fraud status에 따라 response가 달라질 수 있다. prover가 어떤 request context로 data를 받았는지 provenance에 들어가야 한다.

다섯 번째 실패는 privacy-preserving oracle을 public oracle처럼 쓰는 것이다. DECO-style proof는 private user data를 다룰 수 있다. retention, consent, dispute, revocation, key management, verifier logging이 필요하다.

여섯 번째 실패는 legacy credential conversion을 issuer authority로 착각하는 것이다. DECO가 legacy data를 anonymous credential로 옮기는 use case를 보였다고 해서 original website가 credential issuer로 의도적으로 보증한 것은 아닐 수 있다. origin provenance와 credential issuer trust를 분리해야 한다.

일곱 번째 실패는 proof freshness를 oracle update cadence로 덮는 것이다. oracle이 latest fact를 가지고 있다고 말하려면 proof의 timestamp, challenge, source data validity, refresh interval이 필요하다. 오래된 TLS response가 smart contract state를 움직이면 oracle risk가 된다.

여덟 번째 실패는 "no server-side modification"을 "no server dependence"로 오해하는 것이다. 서버를 수정하지 않아도 server response format, login flow, anti-automation control, TLS configuration, certificate chain, compression behavior에 의존한다. 사이트가 HTML을 바꾸면 parser와 predicate가 깨질 수 있다.

아홉 번째 실패는 oracle output을 privacy-free로 생각하는 것이다. predicate만 공개해도 oracle call timing, wallet address, smart contract interaction, amount, gas payer가 user를 식별할 수 있다. web privacy와 on-chain privacy를 함께 봐야 한다.

열 번째 실패는 paper use case를 production guarantee처럼 옮기는 것이다. 논문 application은 feasibility demonstration이다. production deployment는 service-specific legal basis, user consent, availability, dispute resolution, support handling을 요구한다.

## Minimal Lab or Trace

oracle policy trace:

```txt
oracle accepts:
  source allowlist
  TLS support profile
  parser version
  predicate version
  freshness window

oracle emits:
  claim id
  source class
  proof reference
  policy version
```

governance table:

| item | owner | change risk |
|---|---|---|
| parser | oracle team | wrong field |
| predicate | product team | wrong meaning |
| source list | risk team | fake source |
| verifier key | security team | stale trust |
| retention | privacy team | over-collection |

이 worksheet의 핵심은 DECO-style proof를 "암호학이 보증하는 사실"과 "oracle이 운영 정책으로 받아들이는 사실"로 나누는 것이다. 둘 중 하나라도 빠지면 application은 provenance가 있는 데이터와 의사결정 가능한 claim을 혼동한다.

DECO-style trace worksheet:

```txt
scenario:
  user proves ageOver18

source:
  government portal response

hidden:
  name
  exact birthdate
  account token

public:
  origin
  predicate true
  freshness
  verifier policy
```

assumption table:

| assumption | check |
|---|---|
| server identity | certificate policy |
| TLS version | protocol support |
| request context | path and parameters |
| predicate | schema definition |
| oracle trust | verifier policy |
| privacy | disclosure set |

negative cases:

```txt
old response:
  freshness reject

wrong locale:
  parser reject

untrusted oracle:
  app reject

full birthdate leaked:
  privacy failure
```

이 lab은 DECO를 구현하지 않는다. DECO-style architecture의 trust assumption을 table로 분해한다.

comparison trace:

```txt
DECO-like:
  user proves predicate
  oracle verifies
  app consumes fact

TLSNotary-like:
  prover gets receipt
  verifier checks opening
  app parses disclosure
```

두 trace 모두 origin data를 portable하게 만들지만, proof artifact와 trust owner가 다르다. 이 차이를 알아야 "zkTLS"라는 umbrella term 아래의 설계를 비교할 수 있다.

## zkTLS Bridge

DECO 계열 설계는 zkTLS를 단일 protocol 이름으로 보지 않게 만든다. 한쪽에는 TLS origin provenance가 있고, 다른 한쪽에는 private data를 숨긴 predicate proof가 있으며, 그 사이에는 oracle 또는 verifier policy가 있다. 따라서 구현 선택은 "DECO냐 TLSNotary냐"보다 "누가 원문을 보는가", "누가 predicate를 정의하는가", "누가 최종 claim을 책임지는가"로 정리해야 한다.

decision matrix:

| need | design pressure |
|---|---|
| hide raw field | ZK predicate |
| portable receipt | signed attestation |
| direct verifier | MPC-TLS style |
| app-level oracle | DECO style |
| fast UX | delegated verifier |

이 matrix는 우열표가 아니다. 특정 product가 금융 잔액, 나이, 구독 상태, 구매 이력 중 무엇을 증명하느냐에 따라 verifier privacy, latency, revocation, dispute handling의 우선순위가 달라진다.

또 하나의 bridge는 documentation 방식이다. DECO paper는 문제와 가능성을 압축해서 보여주고, production system은 claim catalog, parser contract, verifier policy, audit event schema를 따로 문서화해야 한다. 연구 lineage를 product guarantee로 옮길 때는 논문 문장을 그대로 인용하는 것보다 어떤 artifact가 그 문장을 운영에서 책임지는지 표시하는 편이 안전하다.

DECO는 zkTLS의 뿌리 질문을 선명하게 만든다. 웹 service를 수정하지 않고, 사용자가 TLS로 얻은 private data에 대해 third party가 검증 가능한 statement를 만들 수 있는가? 이 질문은 TLSNotary, proxy mode, MPC-TLS, selective disclosure, VC bridge 모두의 공통 배경이다.

zkTLS design note:

```txt
do not collapse:
  origin provenance
  oracle trust
  ZK predicate
  user consent
  application reliance
```

DECO를 읽을 때는 "oracle이 무엇을 알게 되는가", "server가 바뀌어야 하는가", "TLS version 가정은 무엇인가", "predicate는 어디서 정의되는가", "application은 누구를 신뢰하는가"를 같이 묻는다.

이 질문들은 구현 선택으로 이어진다. oracle이 data를 보지 않아야 한다면 predicate proof가 필요하다. application이 proof를 직접 검증할 수 없다면 oracle attestation을 받아야 한다. server가 format을 자주 바꾸면 parser governance가 필요하다. TLS 1.3/ECH가 필수 환경이면 해당 protocol support를 확인해야 한다.

## Verification Checklist

- DECO의 problem statement를 TLS data provenance로 설명했는가?
- server-side modification과 trusted hardware claim을 논문 맥락으로 제한했는가?
- oracle, prover, verifier, application role을 분리했는가?
- TLS version과 modern deployment caveat를 과장 없이 다뤘는가?
- predicate semantics와 request context failure를 포함했는가?
- TLSNotary와 비교할 축을 만들었는가?
- zkTLS bridge에서 origin provenance와 oracle trust를 분리했는가?
