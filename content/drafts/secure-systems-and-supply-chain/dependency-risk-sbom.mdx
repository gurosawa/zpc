# Dependency risk와 SBOM

## Reader Question

SBOM은 취약점을 자동으로 제거하지 않는다. 그렇다면 왜 중요한가? SBOM은 software bill of materials, 즉 소프트웨어 구성 요소와 그 관계를 기록하는 machine-readable inventory다. 그 자체가 보안 보장은 아니지만, 어떤 component가 어떤 version으로 어떤 artifact 안에 들어갔는지 모르면 취약점 대응, license 검토, 공급망 provenance, 영향 분석을 시작할 수 없다.

Dependency risk의 핵심은 "내 코드가 안전한가"보다 넓다. verifier binary, prover library, circuit compiler, WASM runtime, container base image, transitive package, build plugin, code generator가 모두 결과물에 영향을 줄 수 있다. SBOM은 이 universe를 보이게 만든다. 보이지 않는 dependency는 취약점 공지가 나와도 영향 여부를 판단할 수 없다.

## Why It Matters

CISA의 SBOM 자료는 SBOM을 software supply chain transparency의 기반으로 다룬다. 2025 Minimum Elements 자료는 2021 NTIA minimum elements 이후 tooling과 implementation maturity를 반영해 업데이트된 guidance로 제시된다. SPDX는 ISO/IEC 5962:2021로 표준화된 specification이고, CycloneDX는 OWASP Foundation과 Ecma International 기반의 modular BOM specification으로 components, services, dependencies, vulnerabilities, formulation 같은 supply chain 정보를 표현한다.

zkTLS 시스템은 암호학 protocol만으로 신뢰가 끝나지 않는다. proof verifier가 취약한 JSON parser를 쓰거나, circuit build가 compromised dependency를 포함하거나, prover binary가 수정된 package로 빌드되면 proof result가 흔들릴 수 있다. "이 proof가 valid하다"는 판단은 verifier software와 그 dependency chain의 신뢰 위에서 작동한다.

SBOM은 "취약점이 없다"는 증명서가 아니다. 더 정확히는 "취약점이 발견되었을 때 어떤 artifact가 영향을 받는지 빠르게 묻기 위한 index"다. 이 차이를 지키지 않으면 SBOM을 compliance 파일로만 만들고 실제 incident response에는 쓰지 못한다.

## Core Model

SBOM의 mental model은 component graph다.

```txt
artifact
  -> component
  -> version
  -> supplier
  -> identifier
  -> relationship
  -> evidence
```

component는 package, library, module, container layer, firmware, service, tool일 수 있다. version은 package manager version만이 아니라 digest, commit, build metadata가 필요할 수 있다. identifier는 PURL, SPDX ID, CPE, package coordinates처럼 도구가 비교할 수 있는 이름이다. relationship은 direct dependency, transitive dependency, generated by, contains, depends on 같은 edge다.

좋은 SBOM은 build artifact와 연결된다.

```txt
build:
  source ref
  artifact digest
  build time
  build tool

sbom:
  component list
  dependency graph
  supplier
  identifiers
  timestamp

response:
  vuln impact analysis
  patch priority
  VEX or status note
```

이 모델에서 SBOM은 vulnerability scanner의 input일 뿐 아니라 incident response의 join key다. 취약점 advisory, package registry, container digest, deployment inventory, verifier release가 같은 component identity로 연결되어야 한다.

## Protocol or System Artifact

간단한 SBOM row:

| field | example |
|---|---|
| component | `serde_json` |
| version | `1.0.x` |
| supplier | upstream project |
| identifier | package URL |
| relationship | verifier depends on |
| artifact | verifier image digest |
| evidence | lockfile and build record |

SPDX와 CycloneDX는 서로 다른 ecosystem에서 널리 쓰인다. SPDX는 license와 software package data exchange에서 강하고, 현재 SPDX 3.0이 current version으로 안내된다. CycloneDX는 object model 안에 components, services, dependencies, vulnerabilities, formulation, declarations 같은 영역을 둔다. 어떤 format을 쓰든 중요한 것은 consumer가 읽을 수 있고, build artifact와 연결되고, 업데이트 가능한 데이터로 유지되는 것이다.

SBOM은 다음 artifact와 함께 있어야 쓸모가 커진다.

```txt
lockfile
  resolved package versions

artifact digest
  exact built object

provenance
  where and how built

vulnerability data
  CVE, advisory, exploitability

deployment inventory
  where artifact runs
```

SBOM만 있고 artifact digest가 없으면 어느 release에 해당하는지 모호하다. SBOM만 있고 deployment inventory가 없으면 어디에 배포됐는지 모른다. SBOM만 있고 owner가 없으면 patch decision이 멈춘다.

SBOM과 provenance는 서로 대체물이 아니다. SBOM은 무엇이 들어 있는지를 말하고, provenance는 그 artifact가 어디서 어떤 builder와 입력으로 만들어졌는지를 말한다. SLSA provenance는 output artifact를 subject로 두고 build context를 predicate로 묶는다. 따라서 verifier release를 평가할 때는 "이 digest 안에 어떤 component가 있는가"와 "이 digest가 허용된 builder에서 나왔는가"를 모두 물어야 한다. SBOM scanner가 clean이라고 해도, 승인되지 않은 build runner에서 만들어진 verifier binary라면 배포 gate를 통과하면 안 된다.

## Failure Mode

첫 번째 실패는 stale SBOM이다. release마다 갱신되지 않는 SBOM은 오래된 snapshot이다. dependency update, base image rebuild, transitive dependency change, generated code change가 반영되지 않으면 incident response 때 잘못된 결론을 낸다.

두 번째 실패는 direct dependency만 기록하는 것이다. 취약점은 transitive dependency에서 자주 나온다. package manager lockfile에 있는 dependency graph와 SBOM이 맞지 않으면 scanner는 일부 위험을 놓친다. 특히 build plugin과 code generator처럼 runtime package가 아니지만 artifact를 바꾸는 tool도 중요하다.

세 번째 실패는 component identity 부재다. 이름만 `json`인 component는 advisory와 조인하기 어렵다. ecosystem, supplier, package URL, digest, version, source repo 같은 identifier가 없으면 같은 이름의 다른 package와 섞인다.

네 번째 실패는 SBOM을 보안 보장으로 과장하는 것이다. SBOM은 inventory다. 알려진 취약점이 없다고 해서 unknown vulnerability, malicious maintainer, compromised build, unsafe configuration이 없다는 뜻은 아니다. exploitability, reachability, VEX, patch status, runtime exposure를 별도로 봐야 한다.

다섯 번째 실패는 proof system artifact를 빼는 것이다. zkTLS에서는 circuit source, proving key, verifier key, WASM bundle, native verifier, browser extension, container image가 각각 dependency universe를 가진다. application backend만 SBOM을 만들고 verifier binary를 빼면 proof trust base를 놓친다.

여섯 번째 실패는 scanner output을 dependency ownership으로 착각하는 것이다. scanner가 CVE 목록을 만들 수는 있지만, 어떤 team이 verifier parser dependency를 patch할지, 어떤 deployment가 canary를 받아야 할지, 어떤 customer-facing proof result가 영향을 받는지는 별도 inventory가 필요하다. SBOM은 owner, deployment, provenance, risk decision과 조인될 때 운영 도구가 된다.

## Minimal Lab or Trace

작은 lab은 하나의 verifier release를 기준으로 한다.

```txt
release:
  verifier version
  image digest
  git commit
  build id

collect:
  package lockfile
  container base image
  wasm package list
  native libraries
  build plugins

emit:
  SBOM format
  artifact digest link
  timestamp
  tool name
```

impact trace:

```txt
new advisory:
  package X vulnerable

join:
  package X -> SBOM component
  component -> artifact digest
  digest -> deployment
  deployment -> owner
  owner -> patch plan
```

검증 포인트는 "취약점 이름을 들었을 때 30분 안에 어떤 zkTLS artifact가 영향을 받는지 말할 수 있는가"다. 대답이 package manager search나 manual grep에 의존하면 SBOM과 inventory가 운영 도구로 연결되지 않은 것이다.

## zkTLS Bridge

zkTLS proof pipeline은 여러 software artifact를 통과한다. prover client가 TLS transcript를 다루고, parser가 response를 canonicalize하고, circuit이나 verifier가 predicate를 확인하고, server가 verification result를 저장한다. 각 artifact의 dependency chain이 다르면 위험도 다르다.

예를 들어 JSON canonicalization library에 취약점이 있으면 response field extraction이 달라질 수 있다. WASM runtime에 memory bug가 있으면 verifier crash나 bypass가 가능할 수 있다. circuit compiler dependency가 compromised되면 source는 정상이어도 generated circuit이 달라질 수 있다. SBOM은 이런 질문의 출발점이다.

좋은 zkTLS release metadata는 다음을 묶는다.

```txt
proof component:
  prover
  verifier
  circuit
  parser
  UI

supply chain data:
  SBOM
  provenance
  artifact digest
  signing key
  deployment inventory
```

verifier가 proof만 검증하고 자신이 어떤 binary와 dependency로 동작하는지 추적하지 않으면, proof result의 운영 신뢰가 약해진다.

## Verification Checklist

- SBOM을 취약점 제거 보장이 아니라 component inventory로 설명했는가?
- component, version, supplier, identifier, relationship, artifact digest를 포함했는가?
- SPDX와 CycloneDX를 공식 specification으로 연결했는가?
- direct dependency와 transitive dependency를 구분했는가?
- stale SBOM, missing digest, unknown supplier, no owner를 실패 모드로 다뤘는가?
- vulnerability advisory에서 deployed zkTLS artifact까지 추적하는 trace가 있는가?
- prover, verifier, circuit, parser, WASM runtime dependency를 포함했는가?
