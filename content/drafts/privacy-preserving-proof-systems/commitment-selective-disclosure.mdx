# Commitment와 selective disclosure

## Reader Question

어떤 값을 지금은 숨기고, 나중에는 "바로 그 값"임을 검증 가능하게 열어 보이려면 무엇이 필요한가? commitment는 이 질문에 대한 기본 도구다. commit 단계에서는 값 대신 digest 같은 commitment를 공개하고, open 단계에서는 값과 randomness를 제시해 같은 commitment가 재계산되는지 확인한다.

Selective disclosure는 그 다음 질문이다. 전체 문서나 응답을 공개하지 않고 필요한 claim만 공개하려면, 숨긴 부분과 공개한 부분이 같은 원본에서 왔다는 binding이 필요하다. 단순히 field를 지운 JSON을 보여주는 것은 선택 공개가 아니다. verifier는 공개된 field가 원본 구조의 어디에서 왔고, 어떤 숨겨진 값과 함께 묶여 있었는지 확인할 수 있어야 한다.

W3C VC Data Model 2.0은 issuer, holder, verifier 사이에서 claim을 표현하고 presentation 단계에서 privacy를 고려한다. RFC 9901의 SD-JWT는 JSON claim을 선택 공개하기 위해 salted hash disclosure를 사용한다. BBS cryptosuite는 VC에서 selective disclosure와 unlinkable proof를 제공하는 suite로 정의된다. 이 글의 핵심은 특정 credential format보다 "숨김과 묶음의 분리"다.

## Why It Matters

zkTLS는 웹 origin에서 받은 응답 전체를 공개하지 않고도 "잔고가 100달러 이상이다", "계정 상태가 active다", "배송 주소의 국가가 KR이다" 같은 좁은 statement를 만들고 싶어 한다. 원본 response를 통째로 공개하면 privacy-preserving proof가 아니다. 반대로 공개 claim만 따로 말하면 origin response와의 연결이 약하다.

commitment는 privacy와 integrity를 동시에 다루기 위한 연결점이다. hiding은 commitment만 보고 원래 값을 알아내기 어렵게 하는 성질이고, binding은 나중에 다른 값으로 열기 어렵게 하는 성질이다. 선택 공개에서는 여기에 field path, document schema, domain, freshness, holder consent가 붙는다.

실무에서 중요한 것은 "값"만 commitment하지 않는 것이다. `balance=120`만 묶으면 어떤 계정의 balance인지, 어떤 origin response인지, 어떤 timestamp인지, 어떤 field path인지가 빠진다. zkTLS claim은 값, 맥락, 정책이 함께 묶여야 한다.

## Core Model

commitment mental model:

```txt
commit
  hidden value
  randomness
  domain
  field path
  context
  -> commitment

open
  value
  randomness
  context
  -> verify commitment
```

성질은 두 개로 나누어 기억한다.

| property | 질문 |
|---|---|
| hiding | commitment만 보고 값을 알 수 없는가? |
| binding | 나중에 다른 값으로 열 수 없는가? |

Selective disclosure는 공개 집합을 정하는 policy다.

```txt
original data:
  name
  account id
  balance
  address
  session metadata

disclosed claim:
  balance >= 100

hidden but bound:
  account id
  field path
  response hash
  freshness
```

이 모델에서 verifier는 hidden data를 보지 않지만, 공개된 claim이 임의로 만든 값이 아니라 committed source에서 나온 값임을 확인한다. privacy는 숨긴 field의 부재가 아니라, 공개할 필요 없는 정보를 verifier가 받지 않는 구조에서 나온다.

## Protocol or System Artifact

간단한 commitment pseudo-code:

```txt
domain = "zktls-field-v1"
path = "/account/balance"
value = "120"
salt = random()

commitment =
  H(domain, path, value, salt)
```

검증 pseudo-code:

```txt
open:
  value
  salt
  path
  domain

check:
  H(domain, path, value, salt)
    == commitment
```

RFC 9901 SD-JWT는 claim cleartext 대신 disclosure digest를 issuer-signed JWT 안에 넣고, holder가 verifier에게 필요한 disclosure만 보낸다. verifier는 disclosure를 hash해 signed payload 안의 digest와 맞는지 확인한다. salt entropy, hash algorithm, key binding, claim name concealment 같은 security consideration이 중요하다.

W3C VC 계열에서는 data model과 securing mechanism을 분리해 본다. VC Data Model은 issuer-holder-verifier 역할과 claim container를 정의하고, Data Integrity나 BBS 같은 cryptosuite가 proof와 selective disclosure 방식을 제공한다. 이 분리를 기억해야 "VC라서 자동으로 privacy-preserving"이라는 오해를 피할 수 있다.

## Failure Mode

첫 번째 실패는 salt가 약한 것이다. value universe가 작으면 commitment는 dictionary attack을 당할 수 있다. 예를 들어 status가 `active`, `inactive`, `blocked` 셋 중 하나라면 salt 없이 hash해도 hiding이 되지 않는다. salt는 충분한 entropy를 가져야 하고, 재사용되면 linkability가 생길 수 있다.

두 번째 실패는 domain separation 부재다. 같은 hash가 account balance commitment인지, email disclosure인지, transcript root인지 구분되지 않으면 cross-protocol confusion이 생긴다. domain label과 version을 넣어야 한다.

세 번째 실패는 field path ambiguity다. `/balance`가 account balance인지 reward balance인지 모호하면 verifier가 다른 의미의 값을 같은 claim처럼 받아들일 수 있다. JSON pointer, schema version, canonicalization rule이 필요하다.

네 번째 실패는 hidden claim name leakage다. 값은 숨겼지만 claim name, array length, object shape가 민감한 정보를 드러낼 수 있다. RFC 9901도 claim name concealment와 privacy considerations를 별도로 다룬다. selective disclosure는 공개된 값만이 아니라 남는 metadata를 함께 봐야 한다.

다섯 번째 실패는 consent와 disclosure가 어긋나는 것이다. UI는 "잔고 조건만 공개"라고 말하지만 proof payload가 account id나 timestamp를 함께 공개하면 privacy contract가 깨진다. disclosure set은 machine policy와 user-facing consent text가 같은 source에서 만들어져야 한다.

여섯 번째 실패는 unlinkability를 과장하는 것이다. selective disclosure cryptosuite가 unlinkable proof를 제공해도 credential id, issuer key, rare attribute 조합, presentation timing, verifier-specific metadata가 holder를 다시 연결할 수 있다. privacy는 proof primitive와 metadata minimization이 함께 있어야 한다.

## Minimal Lab or Trace

작은 lab:

```txt
input:
  response field path
  value
  salt
  domain

produce:
  commitment
  disclosure record
  redacted view

verify:
  disclosed value opens
  hidden fields absent
  path is exact
  domain is expected
```

trace table:

| item | public? | bound? |
|---|---|---|
| balance value | yes | yes |
| account id | no | yes |
| field path | yes | yes |
| salt | yes on open | yes |
| response root | yes | yes |
| session token | no | no |

negative tests:

```txt
wrong path:
  reject

wrong salt:
  reject

old domain:
  reject

extra disclosure:
  consent failure
```

이 lab의 목표는 hash 함수를 구현하는 것이 아니다. 공개 claim, 숨겨진 원본, user consent, verifier policy가 같은 binding 구조를 공유하는지 확인하는 것이다.

## zkTLS Bridge

zkTLS에서 selective disclosure는 TLS response와 application claim 사이의 다리다. TLS transcript는 origin authenticity를 주지만, verifier가 전체 response를 볼 필요는 없다. commitment와 selective disclosure가 있으면 "origin response 안의 이 field가 이런 predicate를 만족했다"를 더 좁게 표현할 수 있다.

좋은 zkTLS disclosure receipt:

```txt
origin
response root
field path
claim predicate
freshness
policy id
redaction set
```

여기서 중요한 것은 raw TLS secret, session cookie, bearer token이 commitment open data가 아니라는 점이다. user secret은 witness나 fetch context에 머물러야 하고, public claim은 최소한이어야 한다. commitment는 privacy를 자동 보장하지 않는다. 어떤 정보를 public input으로 내보내는지 설계해야 한다.

## Verification Checklist

- hiding과 binding을 서로 다른 성질로 설명했는가?
- salt entropy와 salt reuse 위험을 다뤘는가?
- domain separation과 version label을 포함했는가?
- field path, schema, canonicalization을 commitment 맥락에 넣었는가?
- selective disclosure가 consent와 verifier policy에 연결되는가?
- SD-JWT, VC Data Model, BBS cryptosuite의 역할을 구분했는가?
- zkTLS claim이 raw response가 아니라 predicate와 receipt로 좁혀지는가?
