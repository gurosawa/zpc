# 키 관리와 crypto period

## Reader Question

강한 알고리즘을 써도 key lifecycle이 틀리면 시스템은 실패한다. 키는 상수가 아니라 운영 자산이다. 생성되고, 배포되고, 사용되고, 회전되고, 정지되고, 폐기된다. 또한 key마다 용도와 사용 기간이 있다. 이 기간을 crypto period라고 부른다. 알고리즘 선택은 보안의 한 조각이고, 키 관리가 그 알고리즘을 실제 시스템 안에서 의미 있게 만든다.

zkTLS에서는 key material이 여러 층에 있다. TLS session traffic secret, notary signing key, verifier public key, circuit verifying key, proving key, policy signing key, search index나 audit log를 보호하는 운영 key가 모두 다르다. "키를 안전하게 보관한다"는 문장 하나로는 부족하다. 어떤 key가 어떤 proof와 decision에 영향을 주는지, 어떤 version이 언제부터 언제까지 valid한지 기록해야 한다.

## Why It Matters

NIST SP 800-57 Part 1 Rev. 5는 key management의 일반 원칙과 key lifecycle, crypto period, algorithm/key length selection을 다룬다. SP 800-57 Part 2는 key management organization과 practice를 다룬다. SP 800-133 Rev. 2는 cryptographic key generation을 다루고, SP 800-131A Rev. 2는 cryptographic algorithm과 key length transition을 다룬다. 이 문서들의 핵심 교훈은 cryptographic primitive가 운영 시간 속에서 관리되어야 한다는 것이다.

TLS 1.3은 handshake마다 session-specific traffic secret을 만들고, long-term certificate key와 ephemeral session secret을 분리한다. zkTLS는 여기에 proof artifact와 verifier ecosystem을 얹는다. 특정 proof가 어떤 verifying key version과 policy key version으로 검증됐는지 모르면 나중에 취소, 회전, 감사, 재검증이 어렵다. key management는 proof correctness의 외부 조건이 아니라 verifier acceptance의 일부다.

RFC 5869의 HKDF와 TLS 1.3 key schedule은 key derivation이 단순 hash가 아니라 label, context, stage를 가진 절차임을 보여준다. handshake secret, application traffic secret, exporter secret은 같은 원천에서 파생될 수 있지만 purpose가 다르다. zkTLS에서 proof key, policy key, audit key를 같은 secret에서 ad hoc으로 만들면 이 purpose separation을 잃는다.

## Core Model

key lifecycle은 다음 상태로 기억한다.

```txt
pre-activation -> active -> deactivated -> compromised/suspended -> destroyed/archived
```

각 key에는 purpose, owner, algorithm, version, validFrom, validTo, revocation status, allowed operation이 필요하다. encrypt key와 signing key, HMAC key와 verifying key, circuit proving key와 verifying key는 lifecycle과 노출 위험이 다르다. 같은 vault에 저장된다고 같은 정책을 쓰면 안 된다.

| Key type | Purpose | Main risk | zkTLS example |
|---|---|---|---|
| TLS traffic secret | session record protection | exposure of session data | response provenance source |
| Notary signing key | attestation authenticity | forged attestation | transcript receipt |
| Circuit verifying key | proof verification | accepting wrong circuit | zk proof acceptance |
| Proving key | proof generation | unauthorized proof creation or leakage | prover service |
| Policy signing key | verifier rule authenticity | policy downgrade | relying app decision |
| Audit log key | evidence protection | tampering or privacy leakage | proof decision history |

## Protocol or System Artifact

minimal key metadata table은 다음과 같다.

| keyId | purpose | version | validFrom | validTo | revokedAt | allowedUse |
|---|---|---:|---|---|---|---|
| vk-balance | circuit verify | 4 | 2026-07-01 | 2026-10-01 | null | verify-only |
| pk-policy | policy sign | 2 | 2026-06-01 | 2026-09-01 | null | sign-policy |
| notary-ed25519 | attestation | 7 | 2026-07-01 | 2026-08-01 | null | sign-receipt |
| vk-old | circuit verify | 3 | 2026-04-01 | 2026-07-01 | 2026-07-02 | reject-new |

proof result envelope에는 최소한 key reference가 들어가야 한다.

```json
{
  "proofId": "proof_01J...",
  "circuitId": "balance-v4",
  "verifyingKeyId": "vk-balance:v4",
  "policyKeyId": "pk-policy:v2",
  "notaryKeyId": "notary-ed25519:v7",
  "issuedAt": "2026-07-03T09:00:00+09:00"
}
```

이 metadata는 secret을 공개하지 않는다. 대신 verifier가 어떤 public key와 policy state로 decision을 내렸는지 재구성하게 한다.

키 관리 artifact에는 data plane과 control plane을 모두 넣어야 한다. data plane은 proof를 만들고 검증하는 데 직접 쓰이는 key다. control plane은 key registry를 서명하고, revocation event를 배포하고, verifier가 어떤 root set을 신뢰하는지 정한다. 많은 사고는 data key 자체보다 control plane drift에서 시작한다.

| Plane | Artifact | Failure if missing |
|---|---|---|
| Data | circuit verifying key | wrong circuit accepted |
| Data | notary attestation key | forged receipt accepted |
| Control | registry signing key | attacker publishes fake active key |
| Control | revocation log | compromised key remains trusted |
| Control | rollout policy | partial deployment accepts inconsistent proofs |

## Failure Mode

첫 번째 실패는 key rotation을 deploy event로만 보는 것이다. 새 verifying key를 배포했지만 old verifier가 여전히 v3 proof를 accept하면, policy와 circuit의 security boundary가 흔들린다. rotation에는 overlap window, reject-new/reject-all policy, rollback rule, audit reason이 필요하다.

두 번째 실패는 revocation을 proof artifact와 분리하는 것이다. notary key가 compromise되어 revoked되었는데 proof envelope가 key id를 담지 않으면 어떤 proof를 재검토해야 하는지 알 수 없다. Certificate Transparency 같은 append-only log model이 중요한 이유도 여기에 있다. key state 변화는 나중에 검증 가능한 evidence로 남아야 한다.

세 번째 실패는 proving key와 verifying key의 위험을 혼동하는 것이다. verifying key는 public일 수 있지만, proving key는 proof system에 따라 민감할 수 있다. 둘을 같은 storage나 access policy로 다루면 generation side risk와 verification side risk를 분리하지 못한다.

네 번째 실패는 crypto period를 business period와 맞추지 않는 것이다. proof는 10분만 유효해야 하는데 verifying key는 1년 valid이고, verifier는 proof `issuedAt`을 보지 않는다. key가 valid하다는 사실은 proof가 fresh하다는 뜻이 아니다. key validity, proof freshness, policy validity는 서로 다른 clock이다.

다섯 번째 실패는 transition plan 없이 algorithm/key length를 바꾸는 것이다. SP 800-131A는 algorithm transition을 별도 주제로 다룬다. production zkTLS에서는 새 curve, 새 hash, 새 proof system, 새 signature scheme이 들어오면 old proof acceptance와 audit compatibility를 함께 설계해야 한다. "강한 것으로 바꿨다"는 말만으로는 migration이 아니다.

여섯 번째 실패는 key custody와 proof privacy를 따로 보는 것이다. prover service가 session material을 오래 보관하면 나중에 compromise되었을 때 과거 사용자의 private response가 위험해질 수 있다. 반대로 모든 material을 즉시 폐기하면 dispute나 audit에 필요한 최소 evidence도 사라질 수 있다. 해결은 secret을 오래 보관하는 것이 아니라, proof id, commitment, key id, revocation state 같은 검증 가능한 metadata를 남기고 secret witness는 짧게 유지하는 것이다.

일곱 번째 실패는 "verify-only" 기간을 설계하지 않는 것이다. 어떤 key는 새 proof 생성에는 쓰지 않지만 과거 proof 검증에는 일정 기간 필요할 수 있다. 이 recipient-usage 성격을 active signing 기간과 구분하지 않으면 old proof를 모두 즉시 깨뜨리거나, 반대로 폐기해야 할 key로 새 proof를 계속 받게 된다.

## Minimal Lab or Trace

다음 trace는 같은 proof를 key state별로 판단한다.

| Proof | verifyingKeyId | key state at verify time | proof age | Decision |
|---|---|---|---|---|
| p1 | vk-balance:v4 | active | 2m | accept |
| p2 | vk-balance:v3 | deactivated | 2m | reject-new or review |
| p3 | vk-balance:v4 | active | 2d | reject: stale proof |
| p4 | vk-balance:v4 | revoked | 2m | reject: key revoked |

pseudo-code는 key validity와 proof freshness를 분리한다.

```ts
if (!keyRegistry.isActive(proof.verifyingKeyId, now)) {
  return "reject: key not active";
}
if (proof.issuedAt < now - policy.maxProofAgeMs) {
  return "reject: stale proof";
}
return verifyProof(proof);
```

이 lab은 "valid key로 만든 old proof"가 항상 accept가 아니라는 점을 보여준다. key state, proof time, policy time을 각각 검증해야 한다.

추가 trace는 verify-only 상태를 다룬다.

| Event | Key state | New proof generation | Old proof verification |
|---|---|---|---|
| rollout starts | active v4, active v5 | v5 preferred | v4/v5 accepted |
| cutoff | verify-only v4, active v5 | v4 rejected | v4 accepted until deadline |
| revocation | revoked v4 | v4 rejected | v4 rejected or manual review |
| archive | destroyed/archived v4 | impossible | metadata-only audit |

이 table은 "폐기"가 단일 버튼이 아님을 보여준다. proof ecosystem에서는 사용 중지, 검증 전용, compromise revocation, archival이 서로 다르다.

## zkTLS Bridge

zkTLS verifier가 받는 것은 proof bytes만이 아니다. 그 proof를 해석하는 key registry와 policy registry도 함께 필요하다. 특정 notary key가 transcript receipt를 만들었고, 특정 circuit verifying key가 predicate proof를 검증하며, 특정 policy signing key가 verifier rule을 승인한다. 이 세 key의 version이 proof public input이나 decision log에 묶이지 않으면 나중에 감사할 수 없다.

또한 zkTLS는 privacy-preserving proof를 다루므로 key compromise의 영향이 단순 data breach보다 복잡하다. compromised proving infrastructure는 허위 proof를 만들 수 있고, compromised policy key는 verifier를 낮은 기준으로 유도할 수 있으며, compromised audit key는 evidence를 바꿀 수 있다. 따라서 key management는 "secret storage"가 아니라 proof ecosystem의 trust management다.

실무적으로는 verifier가 다음 질문에 답할 수 있어야 한다. 이 proof는 어떤 circuit key로 검증됐는가? 그 key는 검증 시각에 active였는가? notary attestation key는 revoked되지 않았는가? policy key가 승인한 rule은 어떤 version인가? old key로 만든 proof를 재검토해야 하는 event가 있었는가? 이 질문에 답하지 못하면 cryptographic proof가 있어도 operational assurance는 낮다.

따라서 Chapter 02의 앞선 primitive들은 key management로 모인다. DRBG와 entropy는 key generation의 입력이다. AEAD와 HMAC은 key scope와 nonce scope를 요구한다. signature와 key exchange는 long-term credential과 ephemeral secret을 분리한다. hash와 commitment는 key id와 policy id를 public statement에 묶는다. crypto period는 이 모든 primitive가 시간이 지나도 같은 의미로 검증되도록 만드는 운영 문법이다.

## Verification Checklist

- key purpose, version, owner, validFrom, validTo, revokedAt을 metadata로 표현했는가?
- key validity와 proof freshness를 별도 clock으로 다뤘는가?
- proving key, verifying key, signing key, policy key의 위험을 구분했는가?
- rotation, revocation, rollback, audit path를 포함했는가?
- proof artifact가 key version과 policy version을 담는가?
- algorithm/key length transition을 old proof acceptance와 함께 고려했는가?
