# Secrets management

## Reader Question

secret은 `.env`에 넣으면 끝나는 값인가? 아니다. secret은 생성, 저장, 배포, 접근 제어, 사용, 감사, 회전, 폐기의 lifecycle을 가진 운영 자산이다. API key, database credential, OAuth client secret, signing key, TLS private key, CI token, webhook secret, Kubernetes service account token, proof service key는 모두 secret이다.

OWASP Secrets Management Cheat Sheet는 secret의 중앙 저장, provisioning, auditing, rotation, management 필요성을 강조한다. NIST SP 800-57은 key management lifecycle을 다루며, NIST SP 800-53은 접근 제어, 감사, system protection control과 secret 운영을 연결한다. 핵심은 secret value 자체보다 누가 어떤 scope로 언제 사용했는지를 통제하는 것이다.

## Why It Matters

zkTLS 시스템은 민감한 secret을 많이 만진다. 사용자의 session cookie나 bearer token은 proof fetch 순간에 필요할 수 있고, verifier service는 signing key나 database credential을 가질 수 있으며, CI/CD는 release signing key와 registry credential을 가진다. 하나라도 새면 origin fetch 권한, proof result, deployment integrity가 흔들린다.

가장 위험한 오해는 "server-side에 있으니 안전하다"는 생각이다. CI log, build artifact, source repository, container layer, error report, browser bundle, mobile app, analytics, support ticket, screenshot, debug endpoint에 secret이 새면 storage 위치가 server였다는 사실은 의미가 없다. secret은 흐름으로 관리해야 한다.

또 다른 오해는 long-lived broad-scope token을 편의상 계속 쓰는 것이다. 만료가 없고, scope가 넓고, owner가 불분명하며, last used time을 모르는 secret은 incident response 때 폐기하기 어렵다. 좋은 secret은 목적이 작고, 수명이 짧고, 사용자가 명확하며, 회전 절차가 검증되어 있다.

운영 관점에서는 secret을 "접근 권한을 가진 데이터"로 본다. 누가 읽을 수 있는지보다 어떤 action을 대신 수행할 수 있는지가 더 중요하다. database password는 row를 읽는 권한이고, signing key는 artifact를 신뢰시킬 권한이며, user token은 사용자의 origin session을 대리하는 권한이다.

## Core Model

secret lifecycle:

```txt
create
  strong generation

store
  managed secret store

grant
  least privilege

use
  short exposure path

audit
  who used what

rotate
  planned and tested

revoke
  fast invalidation

destroy
  no longer recoverable
```

secret metadata는 value보다 중요할 때가 많다.

| field | purpose |
|---|---|
| name | 사람이 이해하는 용도 |
| owner | 회전과 incident 책임 |
| scope | 접근 가능한 resource |
| lifetime | 만료와 재발급 정책 |
| lastUsedAt | dead secret 탐지 |
| rotation | 자동 또는 수동 주기 |
| consumers | 어떤 service가 쓰는가 |
| audit id | 접근 기록 join key |

환경 변수는 전달 방식일 수 있지만 secret management system은 아니다. 환경 변수는 process dump, crash report, child process, debug page, deployment manifest에 노출될 수 있다. 사용한다면 runtime injection, 최소 권한, log redaction, secret scanning, rotation 절차와 함께 써야 한다.

## Protocol or System Artifact

secret inventory row:

```txt
secret:
  verifier-db-password

owner:
  verifier-platform

scope:
  read/write verifier database

storage:
  managed secret store

rotation:
  30 days

lastUsedAt:
  timestamp

audit:
  access events enabled
```

CI/CD artifact:

```txt
job:
  release verifier image

needs:
  registry write token
  signing key access

must not expose:
  token in logs
  key in artifact
  secret in build cache
```

Kubernetes artifact:

```txt
Pod
  -> ServiceAccount
  -> RBAC permissions
  -> mounted token
  -> Secret volume or env
```

Kubernetes Secret은 sensitive data를 저장하는 API object지만, 그 자체가 완전한 secret manager는 아니다. etcd encryption, RBAC, namespace boundary, admission policy, external secret manager integration, workload identity를 함께 봐야 한다. ServiceAccount token도 workload identity와 API access 권한을 만들기 때문에 secret으로 취급해야 한다.

Kubernetes의 secret good practice는 "Secret object를 썼다"에서 멈추지 않는다. Secret을 읽을 수 있는 RBAC 권한은 같은 namespace 안의 여러 workload 권한보다 강할 수 있고, list/watch 권한은 대량 유출 경로가 된다. pod가 Secret을 environment variable로 받으면 process와 diagnostic surface에 남을 수 있으며, volume으로 받아도 file permission, projected token lifetime, workload별 mount 범위를 확인해야 한다. secret posture는 API server, etcd, kubelet, pod runtime, logging pipeline을 모두 지난다.

secret policy artifact는 최소한 세 가지 결정을 포함해야 한다. 첫째, value를 누가 직접 볼 수 있는가. 둘째, workload가 사용할 수는 있지만 사람이 export하지 못하게 할 수 있는가. 셋째, 회전 후 old value가 실제로 거부되는가. 이 세 질문에 답하지 못하면 managed store를 사용해도 운영 통제는 약하다.

## Failure Mode

첫 번째 실패는 secret을 source control에 넣는 것이다. `.env`, test fixture, README, CI config, container build argument, Terraform state에 secret이 들어가면 repository history와 artifact cache에 남는다. 이후 값을 지워도 이미 복제된 history와 logs를 별도로 다뤄야 한다.

두 번째 실패는 CI log 노출이다. build script가 `set -x`나 verbose mode로 command를 출력하고, token이 command argument에 들어가면 log collector에 원문이 남는다. secret masking도 완전하지 않다. masking rule이 prefix나 newline에 깨질 수 있고, encoded secret은 탐지되지 않을 수 있다.

세 번째 실패는 client bundle에 secret을 넣는 것이다. browser나 mobile app에 들어간 secret은 secret이 아니다. public client에서 OAuth client secret을 숨긴다고 믿거나, zkTLS browser extension 안에 privileged API token을 넣으면 공격자가 추출할 수 있다.

네 번째 실패는 broad-scope long-lived token이다. 하나의 token이 read/write/admin 권한을 모두 갖고 만료가 없으면 사고 시 blast radius가 크다. scope를 줄이고, audience를 제한하고, TTL을 짧게 하고, rotation과 revocation을 자동화해야 한다.

다섯 번째 실패는 rotation을 문서로만 둔 것이다. secret rotation은 실제 consumer가 reload하고 old secret이 폐기되는지까지 검증해야 한다. rotation 후 service가 재시작해야만 적용되거나, rollback이 old secret을 요구하면 절차가 깨진다.

여섯 번째 실패는 사용자 session token을 저장하는 것이다. zkTLS proof fetch는 user session을 일시적으로 사용할 수 있지만, verifier나 backend가 그 token을 저장하면 사용자 계정 접근 권한을 보관하는 셈이다. proof의 private witness와 운영 secret을 분리해야 한다.

일곱 번째 실패는 audit 없는 secret access다. 누가 언제 어떤 secret을 읽었는지 모르면 leak source를 찾을 수 없다. 특히 service-to-service credential은 사람이 직접 보지 않아도 access event와 workload identity를 남겨야 한다.

여덟 번째 실패는 secret zero 문제를 무시하는 것이다. secret manager에 접근하려면 bootstrap identity가 필요하다. 이 identity가 static cloud key나 broad CI token이면 모든 secret 관리가 다시 하나의 long-lived secret에 의존한다. workload identity, short-lived federation token, hardware-backed key, restricted runner identity처럼 bootstrap credential 자체의 scope와 lifetime도 설계해야 한다.

아홉 번째 실패는 rotation을 장애 대응 절차로만 보는 것이다. 정기 회전은 rehearsal이다. 실제 leak이 발생했을 때 어떤 service를 재시작해야 하는지, dual-secret window가 필요한지, cache가 old value를 붙잡는지, rollback이 old credential을 요구하는지 미리 검증한다. rehearsal이 없으면 incident 때 회전은 보안 조치가 아니라 outage risk가 된다.

## Minimal Lab or Trace

작은 lab은 secret inventory와 leak path를 함께 만든다.

```txt
inventory:
  name
  owner
  scope
  storage
  consumers
  rotation
  lastUsedAt
```

trace:

```txt
1. generate secret
2. store in managed store
3. grant workload access
4. run service
5. confirm no log exposure
6. rotate secret
7. revoke old secret
8. verify old value fails
```

bootstrap trace:

```txt
workload starts
  -> obtains short token
  -> reads scoped secret
  -> uses credential
  -> emits audit event
  -> token expires
```

leak scan:

```txt
search surfaces:
  source tree
  CI logs
  container layers
  deployment manifests
  crash reports
  browser bundle
  support exports
```

이 lab의 pass condition은 "secret value를 볼 수 없다"만이 아니다. old secret이 더 이상 통하지 않고, access event가 남고, owner가 rotation 결과를 확인할 수 있어야 한다.

## zkTLS Bridge

zkTLS에서 secret은 세 종류로 나눠야 한다. 첫째, user secret이다. session cookie, bearer token, CSRF token은 proof witness일 수 있지만 system secret store에 저장하면 안 된다. 둘째, service secret이다. verifier database credential, signing key, queue credential은 service owner가 관리한다. 셋째, cryptographic material이다. proving key, verifier key, circuit hash, release signing key는 artifact provenance와 연결된다.

이 구분이 없으면 설계가 위험해진다. user token을 backend에 보내 장기 저장하면 proof delegation이 credential delegation이 된다. release signing key를 CI job 어디서나 읽을 수 있으면 악성 verifier binary가 배포될 수 있다. notary credential이 broad scope면 하나의 compromise로 여러 origin proof path가 깨질 수 있다.

좋은 zkTLS secret rule:

```txt
user token:
  never stored
  never logged
  private witness only

service secret:
  managed store
  workload identity
  least privilege

signing key:
  restricted access
  auditable use
  rotation plan
```

## Verification Checklist

- secret을 lifecycle 자산으로 설명했는가?
- generation, storage, grant, use, audit, rotation, revocation, destruction을 다뤘는가?
- environment variable과 secret manager를 혼동하지 않았는가?
- CI log, container layer, client bundle, support export를 leak surface로 포함했는가?
- broad-scope long-lived token을 failure mode로 다뤘는가?
- Kubernetes Secret과 ServiceAccount token의 권한 의미를 설명했는가?
- zkTLS user session token 저장 금지와 private witness 경계를 명시했는가?
